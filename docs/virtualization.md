# Virtualization

**Windowing** is the technique behind everything on this page: instead of mounting a whole collection at once, render only the rows near the current scroll position, plus a small buffer on each side called **overscan**, and reposition that window as the reader scrolls. cinder ships three separate implementations of that idea, all live in the shipped package at the same time. The mapping is many-to-many rather than one engine per component: the fixed-height primitive backs both VirtualList's default mode and DataTable, and the vendor engine backs both DataGrid and Tree. Which one you're looking at is not an accident of when it was written; it's an enforced boundary, tied to which component owns the decision rather than to how the data happens to be shaped. This page maps engine to component, explains that boundary, and says which component to reach for.

## Choosing a component

Four cinder components window a scrolling collection, and the first question is not how many axes you need — it is what your data already is. Semantics come first, dimensionality second: a component that matches your data brings interaction and accessibility behaviour with it that you would otherwise have to rebuild by hand inside a row snippet.

- **Tabular data in a native table** — [`DataTable`](../packages/components/src/components/data-table/README.md), whose [`virtualized`](../packages/components/src/components/data-table/data-table.types.ts) mode windows fixed-height body rows while keeping real `<table>` semantics.
- **A hierarchy that expands and collapses** — [`Tree`](../packages/components/src/components/tree/README.md), whose [`virtualized`](../packages/components/src/components/tree/tree.types.ts) mode flattens the visible order and windows that, keeping `treeitem` semantics and expansion state. Rows are effectively fixed-height there; see the trade-off notes below before planning around a variable-height row.
- **Grid interaction, or columns that need windowing of their own** — [`DataGrid`](../packages/components/src/components/data-grid/README.md), which windows both axes of one scrolling surface and owns `role="grid"`: row and cell focus, keyboard navigation, range selection, column sizing and pinning.
- **Anything else that is fundamentally a list** — [`VirtualList`](../packages/components/src/components/virtual-list/README.md), which windows a single axis, vertical by default or inline under [`horizontal`](../packages/components/src/components/virtual-list/virtual-list.types.ts), and hands you the row snippet. You own every pixel inside a row, including as many columns as you like, as long as the whole row mounts and scrolls together as one unit.

Dimensionality only decides the last two. Reach for `DataGrid` when the columns themselves need independent virtualization or grid interaction semantics; reach for `VirtualList` for a list, however wide its rows are. Choosing `VirtualList` for something that is really a table or a tree does not fail loudly — it just means reimplementing the semantics the other component already has.

### Two-dimensional data is composition over DataGrid, not a new component

> [!NOTE] No `virtual-grid` component exists or should be created
> Two-dimensional virtualization is DataGrid's [`virtualizeRows`](../packages/components/src/components/data-grid/data-grid.types.ts) and [`virtualizeColumns`](../packages/components/src/components/data-grid/data-grid.types.ts) props turned on together, not a separate primitive — with one limit worth knowing before you plan around it: column virtualization is **left-to-right only**. `data-grid.svelte` includes `!isRightToLeft` in `shouldVirtualizeColumns`, so a right-to-left grid keeps every unpinned column mounted however wide it is. Turning both props on there windows rows and nothing else, and cinder has no two-axis right-to-left path today. Internally this really is two independent axes: [`DataGridVirtualizationAdapter`](../packages/components/src/components/data-grid/_internal/virtualization-adapter.svelte.ts) constructs two separate `Virtualizer` instances, `#rowVirtualizer` and `#columnVirtualizer`, composed inside one component with one ARIA grid and one set of column definitions. If a future need looks like "VirtualList but two-dimensional," the answer is DataGrid with both virtualization props on, not a new `virtual-grid` primitive.

## Why cinder has three engines instead of one

The split is enforced in tooling, not just documented. [`scripts/check-virtual-list-dependency-free.ts`](../packages/components/scripts/check-virtual-list-dependency-free.ts) is wired into `lint:invariants` and CI-gated: it walks every file under `virtual-list/` plus `fixed-virtual-window.ts`, and fails the build if any of them imports `@tanstack/virtual-core`, or any other bare specifier that isn't already declared in the package's `dependencies`. Three exceptions are deliberate, and a maintainer extending VirtualList should know them: `classifySpecifier` permits `svelte` and `svelte/*`, and Node and Bun builtins, none of which are listed as dependencies; and test-only files may import development dependencies. The rule is really "no undeclared bare imports in shipped source". Its own header states the reasoning directly: `tree` and `data-grid` already depend on `@tanstack/virtual-core`, but VirtualList's whole design point is a small, dependency-free measurement and offset engine. A companion Bun test, [`_internal/dependency-free.test.ts`](../packages/components/src/components/virtual-list/_internal/dependency-free.test.ts), asserts the same invariant independently, so `bun run --filter=@lostgradient/cinder test` catches a violation locally without needing CI.

DataGrid took the vendor path for a different reason, recorded in [DataGrid: buy-vs-build decision](./decisions/data-grid-buy-vs-build.md): DataGrid's job is much larger than VirtualList's, spanning row _and_ column virtualization, ARIA grid semantics, and selection in one component, and of that whole list, the virtualization math (visible-range computation, scroll-offset tracking, dynamic sizing) was judged the one piece a battle-tested, MIT-licensed, headless library genuinely de-risks. `Tree` also depends on `@tanstack/virtual-core`, through its own [`TreeVirtualizer`](../packages/components/src/_internal/use-virtualizer.svelte.ts), for the same guard script's stated reason. So the boundary isn't "vendor library for the hard case, hand-rolled for the easy one": VirtualList's `dynamicSize` mode, covered below, is in fact its hardest case, and it's still hand-rolled on purpose. The boundary is which component owns the decision. VirtualList is bound by an enforced design constraint to stay dependency-free; DataGrid and Tree are not.

## `fixed-virtual-window.ts`: the fixed-height primitive

[`fixed-virtual-window.ts`](../packages/components/src/utilities/fixed-virtual-window.ts) is pure arithmetic with no imports at all: no DOM, no framework, no vendor code. `getFixedVirtualWindow` takes an `itemCount`, a uniform `itemHeight`, a `scrollOffset`, a `viewportHeight`, and an `overscan`, and returns the window of rows to mount: their indexes, keys, pixel `start` offsets, and the `leadingSize`/`trailingSize` padding that keeps the scrollbar at the right total length. Because every row is assumed exactly `itemHeight` tall, locating the visible window is `O(1)`: `Math.floor(scrollOffset / itemHeight)` for the start index, no measurement and no cache required. Two small guards keep the arithmetic honest against bad input: `resolveVirtualItemHeight` falls back to a caller-supplied default (`1` when the caller omits it, as `VirtualList` does; `DataTable` passes `44`) for a non-finite or non-positive `itemHeight` rather than dividing by zero, and `resolveVirtualOverscan` floors and clamps overscan to a non-negative integer. A third helper, `parsePixelLength`, parses a literal `'NNpx'` string back into a number, returning `undefined` for anything else including relative units like `'20rem'`.

This is `VirtualList`'s default mode, used whenever `dynamicSize` is left `false`, and it is also `DataTable`'s only virtualization mode: [`data-table.svelte`](../packages/components/src/components/data-table/data-table.svelte) calls the same `getFixedVirtualWindow` for its fixed-height, append-only row virtualization, and both components use `parsePixelLength` the same way, to get an initial viewport-height estimate from a `height` prop string before the container has actually been measured. `fixed-virtual-window.ts` lives under `utilities/`, not inside `virtual-list/`, because it's genuinely shared: per the [Tabular component boundaries](./decisions/tabular-families.md) decision, DataTable owns the data-shaped native-table contract and gets fixed-height virtualization as a convenience for large append-only datasets, while grid-style interaction stays DataGrid's job.

## The `dynamicSize` path: measurement without a vendor dependency

Set `dynamicSize` on `VirtualList` when rows genuinely vary in size, because they wrap, embed images, or hold user content, and a single assumed `itemHeight` would be wrong. This mode is still dependency-free in the CIN-204 sense: no `@tanstack/virtual-core`. It is not free of the DOM, though; a single component-owned `ResizeObserver` watches every mounted row and reports its real size.

Two layers do the work, and they're deliberately separated. [`_internal/measurement-window.ts`](../packages/components/src/components/virtual-list/_internal/measurement-window.ts) is the pure engine; its own header states the same "no DOM, no runes, no `ResizeObserver`" invariant, held to a 100%-line, 100%-function coverage floor because none of it needs a live browser to exercise every branch. [`_internal/virtual-list-measurement-store.svelte.ts`](../packages/components/src/components/virtual-list/_internal/virtual-list-measurement-store.svelte.ts) is the reactive layer wrapped around it: a plain `Map<VirtualListKey, number>`, deliberately not a `SvelteMap`, caching each row's measured size by its `VirtualListKey`, plus a queue of the scroll corrections those measurements imply. It's a plain `Map` because consumers re-derive off one `version` `$state` counter rather than subscribing per key, which matters on a list with tens of thousands of rows.

`buildVirtualOffsets` turns that size cache into a cumulative offsets table, where `offsets[i]` is the pixel sum of every slot before `i`, rebuilt in full on every call because a single new measurement invalidates every later offset anyway, so an incremental patch would buy nothing; callers memoize the rebuild behind a value derived from item count and the cache's `version`. `findOffsetIndex` binary-searches that table for the last index whose offset is at most a target pixel position, and `getDynamicVirtualWindow` uses it to locate the visible window, then walks outward by `overscan`. That overscan is applied symmetrically, subtracted from the start and added to the end, each clamped independently, which is a deliberate divergence from `fixed-virtual-window.ts`'s `endIndex = startIndex + visibleCount + overscan * 2` formula: the fixed engine's shape is an artifact of how it clamps at index 0, not a rule the dynamic engine has to follow too, and the module's own comment says explicitly not to "fix" the divergence to match.

Recording a measurement (`record()`) stores it at full precision, never rounded, because quantizing thousands of rows measured to a fraction of a pixel each would compound into a total height that's meaningfully short. A report within `0.01` pixels (`MEASUREMENT_EPSILON`) of the cached value is treated as unchanged: no version bump, no queued correction. That epsilon is what stops a feedback loop where writing a corrected scroll offset re-lays-out a row, whose `ResizeObserver` reports the same size back, which would otherwise queue another correction indefinitely. When a measurement genuinely differs from what the offsets table assumed, the pending correction is drained inside an `$effect.pre` and turned into a corrected scroll target, which is then applied to the scroll container in a paired `$effect` that runs after Svelte has patched the DOM for the new measurement but still before the browser paints, so the scroll position lands in the same frame the layout changed and the reader never sees a jump. Buying that correction costs the mode the browser's own scroll anchoring: `virtual-list.css` sets `overflow-anchor: none`, but only on `.cinder-virtual-list[data-cinder-dynamic-size='true']`, scoped to `dynamicSize` specifically, because `dynamicSize` owns anchoring itself and the two mechanisms would otherwise fight over the same scroll position; fixed-height rows never resize, so native anchoring is left alone there.

The two `VirtualList` modes aren't fully disjoint even so. Both build a small `VirtualItemLocator`, a pair of `getStart`/`getSize` functions for a row index, and share one function, `computeScrollToIndexOffset`, to resolve `scrollToIndex`'s `align` options: `'start'`, `'center'`, `'end'`, and `'auto'`, the last of which no-ops when the target row is already fully visible. The fixed mode's locator is `index * itemHeight` arithmetic; the dynamic mode's locator reads the offsets table. Same alignment logic, two different sources of `start` and `size`.

## `@tanstack/virtual-core`: two-axis virtualization for DataGrid and Tree

DataGrid's row and column virtualization are each opt-in, `virtualizeRows` and `virtualizeColumns`, both defaulting to `false`, and both are backed by [`_internal/virtualization-adapter.svelte.ts`](../packages/components/src/components/data-grid/_internal/virtualization-adapter.svelte.ts)'s `DataGridVirtualizationAdapter`, which constructs two independent `Virtualizer` instances from `@tanstack/virtual-core`. Despite the vendor library's own support for measured, dynamic sizing, DataGrid's public contract is fixed-height rows only: `rowHeight` is documented as the "fixed body-row pixel height used by row virtualization," defaulting to 44, and nothing in `data-grid.svelte` wires the adapter's `measureElement` attachment into a rendered row. Column virtualization similarly windows over declared widths, not measured ones: the column virtualizer's `estimateSize` reads `getColumnWidth(index)` directly, and per DataGrid's README, `virtualizeColumns` only virtualizes left-to-right and only for unpinned columns; pinned columns stay rendered. That's a real contrast with `VirtualList`'s `horizontal` mode, which resolves right-to-left layout from the container's own computed writing direction at mount.

Needing a live browser is also new here. `fixed-virtual-window.ts` and `measurement-window.ts` are both pure functions, callable from a Bun test with no DOM at all; `DataGridVirtualizationAdapter` explicitly no-ops (`typeof window === 'undefined'`) until it's running in one, because it has to hand `@tanstack/virtual-core` its own `observeElementRect` and `observeElementOffset` options, and those are the functions that open a real `ResizeObserver` and a `scroll` listener against a real scroll element for the vendor to read from. Wrapping the vendor library also costs upkeep the two hand-rolled engines don't need: the adapter maintains its own `#fallbackRows`/`#fallbackColumns`, computed independently of the vendor virtualizer, and overrides the vendor's window with that fallback whenever the vendor's window comes back empty, or, once the reader has scrolled past the top, whenever the vendor's first visible index differs from the fallback's by more than one. That reconciliation logic is itself part of what cinder maintains; it isn't something `@tanstack/virtual-core` handles on its own.

`Tree` is the third consumer of `@tanstack/virtual-core` in cinder, through its own [`TreeVirtualizer`](../packages/components/src/_internal/use-virtualizer.svelte.ts): a single-axis wrapper for [`tree.svelte`](../packages/components/src/components/tree/tree.svelte)'s virtualized mode, which flattens the expand and collapse hierarchy into one visible-order list before virtualizing it. It shares the same `typeof window === 'undefined'`-guarded, fallback-windowed shape as DataGrid's adapter, just with a single `Virtualizer` instead of two.

## Trade-offs at a glance

| Engine                                                    | Axes windowed                | Runtime dependency       | Row sizing                            | Callable without a browser                   |
| --------------------------------------------------------- | ---------------------------- | ------------------------ | ------------------------------------- | -------------------------------------------- |
| `fixed-virtual-window.ts`                                 | one                          | none                     | uniform, assumed                      | yes                                          |
| `dynamicSize` (measurement-window.ts + measurement store) | one                          | none                     | measured and cached per row           | the offset math yes, the `ResizeObserver` no |
| `@tanstack/virtual-core`                                  | two in DataGrid, one in Tree | `@tanstack/virtual-core` | effectively fixed in both — see below | depends on the consumer — see below          |

The last two cells differ by consumer, and a single answer for either would misdescribe one of them.

**Row sizing.** Neither consumer gives you variable-height rows today, though they arrive there differently.

DataGrid's public contract is fixed-height: `rowHeight` defaults to 44 and nothing wires the adapter's `measureElement` into a rendered row, so the vendor's dynamic sizing is simply left unused.

`Tree` looks like the exception and is not. It does attach `virtualizer.measureElement` to every virtual row, and `TreeVirtualizer` does read a bounding-rect height — but `virtualizedRowStyle` gives that same element a definite `block-size` from the current `virtualItem.size`, and `.cinder-tree-item--virtual` sets `overflow: hidden`. The measurement therefore reports the estimate back to the vendor, which can never learn that a `virtualizedItem` is taller than `virtualizationEstimatedRowHeight`; a taller row is clipped instead. So the attachment is real and the measurement is inert.

Worth knowing because it is a general trap rather than a Tree quirk: a definite size on the observed element, plus clipped overflow, makes a `ResizeObserver` report back whatever was imposed on it. VirtualList's own pinned sticky row had exactly this bug — twice, once frozen against growth and once against shrinkage — before it was left unsized. Tree's case is tracked separately.

**Without a browser.** Neither can run the vendor virtualizer: both guard construction on `typeof window === 'undefined'`. What differs is the fallback. `DataGrid` deliberately returns no virtual rows during SSR. `Tree` falls back to its own bounded arithmetic — `TreeVirtualizer.virtualItems` returns `#fallbackVirtualItems()` whenever the vendor window is unavailable or disagrees with it, and `totalSize` likewise returns an estimate — so a server render still produces a windowed result. The distinction is live DOM observation, which neither has on the server, versus a server-callable fallback, which only `Tree` provides.
