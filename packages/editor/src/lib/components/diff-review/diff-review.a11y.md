# DiffReview · accessibility

DiffReview's nearest neighbors are `DiffViewer` and `SourceDiffViewer`. It is admitted as its own component under the behavior-first admission bar because neither viewer, alone or side by side, provides multi-target file navigation, comment lifecycle (create/edit/delete/resolve/reopen), a drafts inventory, reviewed markers, or Markdown/JSON export -- DiffReview composes their public annotation hooks with `diff-review-state` and the export functions to add that behavior without duplicating either viewer's rendering or reaching into a private controller.

## Pattern

DiffReview packages a higher-level workflow (file navigation, diff comparison, comment creation, drafts, export). Confirm the composed controls, labels, states, and keyboard path match the domain task instead of treating the visual shell as the accessibility contract.

Purpose: aggregate single- and multi-target diff review with comment controls, drafts inventory, and Markdown/JSON export.

## Use when

- Reviewing one or many mixed Markdown/source-patch targets and collecting comments for an agent handoff.

## Avoid when

- Rendering a single diff with no comment/export workflow — use `DiffViewer` or `SourceDiffViewer` directly.

## Regions and names

- File navigation: `<nav aria-label="File navigation">`.
- Diff surface: `<main aria-label="Diff">`.
- Review sidebar (drafts inventory + comments panel): `<aside aria-label="Review">`.
- The path filter is a labelled `<input type="search" aria-label="Filter files by path">`.
- Export scope, Copy, and Download controls sit in a single toolbar; a blocked export replaces them with a `role="status"` message naming the exact pending-draft count and a link back to the drafts inventory, rather than disabling the controls silently.

## Keyboard and focus

Every DiffReview-owned control (file buttons, the Reviewed checkbox, the comment composer, drafts actions, toolbar controls, and comment navigation) is a native, keyboard-operable element. Per-line/per-file comment creation reuses `DiffViewer`'s and `SourceDiffViewer`'s own annotation-hook keyboard model (Enter to start/commit, Shift+Arrow to extend, Escape to cancel) documented in each viewer's own `*.a11y.md` — DiffReview does not add a second competing key handler on top of it. Deleting a comment opens Cinder's `ConfirmDialog`; canceling or confirming returns focus to the "Delete" button that opened it (`ConfirmDialog`'s own behavior, exercised end-to-end in `diff-review-keyboard.test.ts`).

## Comment-to-anchor navigation

A comment's "Go to" action, for a CURRENT comment, calls the mounted viewer's own public `focusAnchor`/`focusFile` (through `DiffReviewRenderer`'s unified handle) — switching target/file and Markdown view mode first as needed, exactly as those viewers already do for their own `ref.focusAnchor`. If the anchor's row isn't rendered, a visible `role="status"` message says so. For an OUTDATED or REMOVED comment, "Go to" never focuses the diff at all: focus moves to that comment's own captured-detail text in place, and a REMOVED comment additionally carries a "Removed" badge (a target no longer present in `state.targets`, distinct from "Outdated," whose target is still live but changed). Saved-comment markers (via `lineAnnotation`/`fileAnnotation`) render for CURRENT comments only — an outdated comment deliberately produces no marker, proven by a mixed-status test in `diff-review-renderer.test.ts`.

## Invalid targets, renderer failure, and empty diffs

An invalid `targets` update shows a `role="alert"` with the structured error and keeps the last valid render. A target whose viewer throws while rendering is isolated behind a `<svelte:boundary>`: a local, scoped error replaces just that pane, its own file-comment control is disabled, and every other target/export is unaffected. A file with zero changed lines shows "No commentable patch lines." instead of the viewer.

## Copy and download announcements

Copying announces success only ("Copied review to clipboard.") through a visually hidden `aria-live="polite"` region. A clipboard failure is rendered as **visible, persistent text** (`role="alert"`), not only announced, and never blocks a subsequent download or mutates state — the failure path and the download path share no state.

### Review-fix follow-up (same session, commit `5eefdc8f`)

Writing the tests above surfaced two real shipped-source defects against the ratified contract's "Drafts, modes, and ReviewEditor" section, each fixed with the regression assertion that first caught it (red → green, both confirmed against a real running Playwright browser, not simulated):

1. **Contract: "Open clears only the necessary filters and focuses its composer."** `openDraft` in `diff-review.svelte` switched target/file and set `activeDraftId`, but never touched `filterQuery` and never moved DOM focus into the composer. A draft opened from the inventory while the path filter still hid its file entry left the file list showing zero items and left focus stranded on the "Open" button — the composer was visible but keyboard-inaccessible without an extra, undocumented Tab. Fixed: `openDraft` now clears `filterQuery` only when it is itself hiding the draft's own file entry (never clears an unrelated filter), and a new effect focuses the composer `<textarea>` once it is in the DOM. Regression test: the two added assertions in `diff-review-drafts-inventory.playwright.ts`'s existing "hidden-draft inventory" case (`.diff-review-file-list-item` is nonempty and the composer is focused immediately after Open).
2. **Contract: "If read-only mode has nonempty drafts, export stays blocked and explains that the host must enable editing to save/discard them."** The export gate already stayed correctly blocked, but the composer itself — reachable through the drafts inventory's "Open" action, which always renders regardless of `readonly` — rendered a fully enabled textarea and Save button with no explanation, unlike `DiffReviewComments`' own mutation controls and unlike ReviewEditor's separate diff-comment composer (which COR-512 already fixed for the identical case). Fixed: the composer now disables its textarea and Save button and shows "Enable editing to change or save this draft." when `readonly`, and its Cancel button reads "Close" instead — mirroring `review-editor-impl.svelte`'s existing pattern exactly. Regression test: a new `diff-review-error-states.playwright.ts` case ("read-only with a nonempty draft") using a new `?states=1` fixture mount (`#example-mount-readonly-toggle`) that toggles `readonly` at runtime on a session with an existing draft.

Both fixes are scoped to `diff-review.svelte`; no other component changed. Reviewing the fixes above against the contract found two further real defects and one test-coverage gap, each fixed test-first (red confirmed against the prior commit, then green):

1. **`openDraft`'s filter-clearing condition was still over-broad.** It cleared `filterQuery` whenever the draft's file entry was absent from the _filtered_ list, without first checking whether an entry existed at all under any filter. A draft whose target was removed entirely (contract: "Missing targets retain complete captured drafts/comments") has no entry regardless of filter value, so the filter was never the reason it was hidden — clearing it discarded a filter the host still needed, violating "Open clears ONLY the necessary filters." Fixed: only clear when an entry exists unfiltered but the current filter excludes it. Regression test: `diff-review.test.ts`, "Open on a draft whose target was removed entirely leaves an unrelated path filter untouched."
2. **The prior fix's `disabled` textarea silently defeated its own focus fix in read-only mode.** Item 2 above correctly disables the composer, but a `disabled` `<textarea>` can never receive DOM focus in a real browser — so the very next line's `composerTextareaElement.focus()` (item 1's fix) was a no-op specifically when `readonly`, leaving "Open ... focuses its composer" unmet for exactly the read-only case DR-8's own matrix names ("open hidden drafts" and "inspect read-only ... states," together). This was not caught by the prior session's own regression test for item 2, which asserted `toBeDisabled()` but never `toBeFocused()`. The identical gap existed in `review-editor-impl.svelte`'s mirrored composer, which additionally had **no focus-on-open wiring at all**, in either mode. Fixed in both components: the textarea now uses native `readonly` instead of `disabled` (blocks editing identically; Playwright's `toBeEditable()` still fails on it) while remaining focusable and its text selectable/copyable; `review-editor-impl.svelte` gained the same `composerFocusRequested`-style effect `diff-review.svelte` already had. Regression tests: the existing "read-only with a nonempty draft" case in `diff-review-error-states.playwright.ts` now also asserts `toBeFocused()`; `review-editor-diff-comments.playwright.ts` gained a new editable-mode "Open on a pending draft focuses the reopened composer" case and the same `toBeFocused()` assertion in its own read-only case. The `.diff-review-composer-readonly-note` class referenced by item 2's own text ("mirroring `review-editor-impl.svelte`'s existing pattern exactly") had no matching CSS rule in `diff-review.css` at the time of that claim; added, mirroring `.review-editor-diff-composer-readonly-note`.
3. **`review-editor-impl.svelte`'s "Unsaved drafts" inventory is reachable from either tab, not only the diff tab.** It renders in the shared comments panel outside the `activeView` conditional, so the fix above needed to work when Open is clicked while on the Editor tab (the click both switches `activeView` to `'diff'` and mounts the composer before the focus effect can run). Verified rather than assumed: `review-editor-diff-comments.playwright.ts`'s new case switches to the Editor tab immediately before clicking Open and asserts both the tab switch and the resulting focus.
4. **Keyboard-matrix coverage gap: "Reopen" was never exercised.** The new `diff-review-keyboard-matrix.playwright.ts` and the unit-level "every own control is a native, tab-reachable element" test both only ever seeded an unresolved comment, so only "Resolve" was checked — "Reopen" (one of the contract's own named cases, "create/edit/delete/resolve/reopen") had no tab-reachability or activation assertion anywhere, though the underlying `reopen-comment` reducer action was already covered at the state layer (`reduce-comments.test.ts`, `reduce-readonly.test.ts`). No source defect: added `diff-review-keyboard.test.ts`'s new resolved-comment case, which passed immediately.

**Residual risk, fixed (COR-509 follow-up):** `diff-review.svelte`'s own mutating dispatch calls (`setReviewed`, `updateComposerBody`, `saveComposer`, `saveDraft`, `discardDraft`, and `handleSelectionChange`'s/`addFileComment`'s `create-draft`) previously never passed `{ readonly }` to `dispatchDiffReviewAction`, unlike `review-editor-impl.svelte`'s `dispatchDiffReviewChange`, which forwards `{ readonly: isReadonly }` so the reducer itself rejects a mutation with the `readonly` error code (contract: "underlying action handlers also return `readonly`"). `diff-review-comments.svelte`'s `editComment`/`deleteComment`/`resolveComment`/`reopenComment`/`setReviewNote` had the identical gap. Every UI path to these calls was already correctly gated with native `disabled` or an `{#if !readonly}` guard (verified for the Reviewed checkbox, comment Edit/Delete/Resolve/Reopen, the file-comment entry point, the drafts-inventory Save/Discard, and the review note), so no user-reachable exploit existed in a real browser; it was a defense-in-depth gap only, predating this session (present since DR-6/COR-509). All ten call sites now forward `{ readonly }`, matching `review-editor-impl.svelte`.

Regression coverage, each exercising the handler with the surrounding UI guard deliberately defeated (removing `disabled`, or reaching a control the contract itself keeps available in read-only mode) rather than relying on that guard: `diff-review.test.ts`'s "DiffReview component: readonly rejects mutation at the handler (defense in depth)" suite covers `update-draft` (via the drafts inventory's always-available Open, then typing in the native-`readonly` textarea), `set-reviewed` (force-enabling the Reviewed checkbox), and `save-draft` from the composer (force-enabling Save), plus a structural check that the drafts-inventory list's own Save/Discard have no rendered control left to bypass and a navigation-still-works check for `select-file`. `diff-review-comments.test.ts`'s matching suite covers `set-review-note` (force-enabling the textarea). `editComment`/`deleteComment`/`resolveComment`/`reopenComment` and `addFileComment`'s/`handleSelectionChange`'s `create-draft` remain untested by a UI-bypass technique specifically because there is no `disabled` fallback to defeat: their only controls are removed from the DOM entirely under `{#if !readonly}` (comment actions, file-comment entry point) or the callback that would trigger them is never wired to the underlying viewer at all when read-only (`diff-review-renderer.svelte` omits `onAnnotationSelectionChange` outright, see lines 260/270); those handlers now forward `{ readonly }` for the same defense-in-depth reason but are exercised only by the existing absence assertions (`diff-review.test.ts`'s "readonly hides the file-comment composer entry point", `diff-review-comments.test.ts`'s "readonly hides mutating controls but keeps the filter available"), not by a bypass that reaches the dispatch.
